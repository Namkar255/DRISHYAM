# Local FastAPI and Celery Runtime With External Staging Services

This configuration runs **only** the DRISHYAM FastAPI API and Celery worker on the local computer. PostgreSQL remains in the team-controlled Supabase staging project, Redis remains in the team-controlled Upstash database, and final evidence/report artifacts are written to the private `drishyam-staging-private` Supabase Storage bucket. The local `data/` and `generated_reports/` folders are writable caches and report-rendering workspaces; they are not the authority for staging data.

Copy `.env.example` to `C:\Users\<your-Windows-user>\.drishyam\drishyam-staging.env` and populate the listed values directly from the Supabase and Upstash dashboards. This keeps secrets outside the OneDrive-backed source folder. Do not add that file to a ZIP, Git commit, cloud drive share, or chat message. `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`, and `OTP_PEPPER` are secrets. The Supabase service-role key stays only in the API/worker environment and must never be added to the React frontend.

Use the Supabase **Connection Pooler** connection string with `?sslmode=require` retained. Use the Upstash TLS URL, normally beginning with `rediss://`. Keep `STORAGE_BACKEND=supabase` and the bucket value `drishyam-staging-private`. A new `SECRET_KEY` and a separate new `OTP_PEPPER` can be generated locally using the Windows password generator or any offline password manager.

Once the runtime file is complete, set `DRISHYAM_RUNTIME_ENV_FILE` to its full path for the current PowerShell window and run `docker compose up --build` from this folder. The API is intentionally bound only to `127.0.0.1:8000`; it is not exposed to the local network or the public internet. The API applies Alembic migrations on startup, and the worker consumes only the DRISHYAM evidence/report queues from Upstash. `ALLOW_LOCAL_CONSOLE_EMAIL=true` is permitted only for the localhost synthetic-test flow so verification OTPs are written to the local development mailbox; it must be `false` or absent on a future VPS. Stop both services with `docker compose down`.

The same environment-variable names and Compose services will later transfer to a VPS. The future VPS will use its own private environment file, its own generated secrets where appropriate, a reverse proxy with HTTPS, and a restricted firewall; do not copy the local runtime file to a public repository.
