1. Executive Summary — what actually needs to change

Core finding: DRISHYAM already contains roughly 60% of what SIH26189 requires — but it is dressed for the wrong problem. The evidence-provenance engine is strong and should not be rebuilt. What must change is the entity vocabulary, the shape of the graph, and the presentation layer.

The most important architectural principle recommended by the advisory reports — Evidence → Observation → Claim → Entity/Event/Relationship → Candidate or Verified Graph — is already implemented in this repository. It exists as the chain RawExtractionArtifact → ModelInferenceRun → NormalizedRecord → RecordRelation → RecordReview. The advisory reports could not confirm this because they were written without access to the source repository. This audit confirms it from the code.

The consequence for planning is significant:

  • No rewrite is required. The provenance, review, audit, storage, worker and model-gateway layers are production-shaped and should be retained as-is.
  • The real work is additive. Three additions unlock everything else: a criminal-network entity vocabulary, an entity-to-entity relationship table, and network analytics.
  • The current system is tuned for cyber-fraud, not criminal networks. Its extractors, alert rules and graph shape all assume UPI/phishing investigation. SIH26189 asks for people, vehicles, locations, organisations and their relationship maps.

The three changes that matter most

#ChangeWhy it is decisiveEffort
1 Add Person / Vehicle / Location / Organisation extraction The problem statement names these five entity classes explicitly. Vehicles, locations and organisations are currently not extracted at all. This is the first thing an evaluator will look for. 2–3 days
2 Add an entity_relations table with typed, provenance-bearing edges The current graph connects evidence files to shared identifiers. A criminal network graph connects entities to entities. Entity-to-entity edges do not exist today. 3–4 days
3 Add NetworkX centrality, bridge and community analytics "Identify influential individuals" is an explicit requirement with zero current implementation. NetworkX is already an installed dependency, so this is the cheapest large win. 2 days

4. Gap analysis against SIH26189

SIH26189 requires a system that processes multiple crime and intelligence sources; extracts people, locations, vehicles, phone numbers and organisations; builds relationship maps; identifies influential individuals; detects suspicious patterns; and provides visual and analytical insight for investigators. Each obligation is assessed below.

PS obligation Status Finding
Process multiple sources Partial Generic parsers exist for TXT, EML, CSV, XLSX, PDF and images. There is no CDR adapter and no FIR/police-report adapter — the two sources the problem statement names first. SourceType has no FIR, CDR, SURVEILLANCE or SOCIAL_MEDIA member.
Extract entities Major gap Current vocabulary (extraction/normalizer.py) is: phone, upi_id, email, url, ifsc, account_number, utr, ip_address, person. Vehicle: absent. Location: not an entity (only a plain string field on the record). Organisation: absent. Person extraction requires a literal Name:/Beneficiary: prefix, so it will not fire on free-text FIR narrative.
Build relationship maps Major gap graph/connections.py builds an evidence ↔ identifier bipartite graph — it answers "what do these two files have in common". SIH26189 needs entity → entity edges. RecordRelation only carries corroboration / contradiction between records. There is no CALLED, TRANSFERRED_TO, LOCATED_AT or USED_VEHICLE anywhere in the codebase.
Identify influential individuals Absent A repository-wide search for centrality, betweenness, pagerank, community and louvain returns zero results. NetworkX is already installed and used only for a provenance projection.
Detect suspicious patterns Wrong domain The five existing rules are HIGH_VALUE_TRANSFER, REPEATED_RECIPIENT, RECURRING_IDENTIFIER, PHISHING_LINK, RAPID_TRANSACTION_SEQUENCE. These are payment-fraud rules. They are well built — explainable, idempotent, evidence-linked — but they do not address criminal-network patterns.
Temporal analysis Absent No incident window on the Case model, no before/after analysis, no communication-burst detection. The timeline is a chronologically sorted list only.
Visual / analytical insight Partial Sixteen workspace views exist, but there is no Entity Profile screen, no Relationship Detail drill-down, and no graph filtering, hop-expansion or path highlighting. The differentiating chain graph → relationship → claim → evidence → original source cannot currently be clicked through in the UI.
Actionable intelligence Partial The Trace Orb assistant is deliberately and correctly isolated from case data. A separate case-grounded, permission-aware, source-citing assistant does not exist.

ItemSeverityFinding and required action

Version control stateHigh The repository has a single commit. Deployment expectationMedium docker-compose.yml defines only api and worker — no PostgreSQL, no Redis. Both are external services, so the stack cannot be brought up by a judge or a new team member without the private environment file. A self-contained demo profile is required.

5. Explicit non-goals — what we are deliberately NOT building

The advisory reports recommend several additions that this audit rejects on the basis of what the repository actually contains. Each rejection is stated with its reason so the decision can be defended if questioned.

We will not add Neo4j.
Two of the advisory reports suggest Neo4j as a graph projection. The expected case graph is a few thousand nodes. NetworkX is already an installed dependency and is sufficient at that scale. Adding Neo4j means another container, another migration path, another failure mode, and no visible benefit in a demonstration. One of the reports itself concedes "NetworkX for MVP". We follow that. PostgreSQL remains the authoritative system of record either way.
We will not switch OCR engines to PaddleOCR.
The stated reason for PaddleOCR is bounding boxes and layout coordinates. The existing pytesseract.image_to_data implementation in evidence_intelligence/ocr.py already produces bounding boxes, block-level confidence and quality flags. PaddlePaddle wheels are large and version-sensitive and would put the Docker build at risk close to the event. The real accuracy improvement comes from OpenCV preprocessing applied before OCR — that is what we will add instead.
We will not rewrite the model gateway for OpenAI.
One report specifies building a VisionExtractionService interface. That interface already exists as ModelRouter with a providers/base.py protocol and three implementations. The correct change is to add one file, providers/openai.py, conforming to the existing protocol — approximately 120 lines. Nothing above the provider layer changes.
We will not hard-code any model identifier.
Model names must continue to arrive from environment variables, exactly as OLLAMA_VISION_MODEL and GROQ_MODEL do today. Model identifiers quoted inside advisory documents must be verified against the live provider catalogue before use and must never be embedded in source.
We will not connect the Trace Orb assistant to case data.
Trace Orb is intentionally isolated: it uses a separate credential block so that a website help assistant can never reach evidence. This is a correct safety boundary and a defensible design point in evaluation. The case-grounded assistant will be a separate service reading only database rows.
We will not add blockchain, Kubernetes, Kafka, a service mesh or a vector database.
All three advisory reports agree, and this audit agrees. Hash chains, lineage records, audit logs and access control already provide the integrity story. Infrastructure added for appearance costs schedule and invites questions the team cannot answer with measurements.

The entity_relations table

class EntityRelation(Base):
    """A typed, provenance-bearing edge between two resolved entities.

    Invariant: an edge is never inserted without source_evidence_id and
    source_reference. A relationship without provenance is not investigative
    intelligence and must not reach the graph.
    """
    __tablename__ = "entity_relations"

    id                  : str            # uuid
    case_id             : FK cases.id            (indexed, CASCADE)

    subject_entity_id   : FK entities.id         (indexed)
    object_entity_id    : FK entities.id         (indexed)
    relation_type       : String(32)     # CALLED | MESSAGED | TRANSFERRED_TO
                                         # LOCATED_AT | USED_VEHICLE
                                         # MENTIONED_WITH | ASSOCIATED_WITH_CASE

    source_evidence_id  : FK evidence_files.id   (NOT NULL)
    source_record_id    : FK normalized_records.id (nullable)
    source_reference    : JSON           # bbox, page, or CSV row  (NOT NULL)

    observed_at         : DateTime | None
    time_precision      : String(16)     # reuse TimePrecision vocabulary
    support_count       : Integer        # independent records supporting this edge
    supporting_record_ids : JSON

    extraction_method   : String(64)
    confidence          : Numeric(5,4)
    verification_status : String(32)     # machine_extracted | needs_review
                                         # human_verified | rejected | superseded

    reviewed_by_id      : FK users.id | None
    reviewed_at         : DateTime | None
    idempotency_key     : String(255)  UNIQUE
    created_at          : DateTime

    __table_args__ = (
        Index("ix_entity_relations_case_type", "case_id", "relation_type"),
        Index("ix_entity_relations_subject",   "case_id", "subject_entity_id"),
        Index("ix_entity_relations_object",    "case_id", "object_entity_id"),
        Index("ix_entity_relations_time",      "case_id", "observed_at"),
    )
Why the unique idempotency_key matters. Reprocessing the same evidence must not duplicate edges. The key is derived from case_id + relation_type + subject + object + source_record_id. This mirrors the pattern already used in alerts/rules.py and RecordRelation, so it is consistent with the existing codebase.

7. The roadmap — Phase 0 to Phase 9

Phases are ordered by demonstration visibility, not by architectural tidiness. The system remains demonstrable after every phase. Each phase states exactly what changes and what the change produces.

Phase 0 — Repository hygiene and correct positioning
Effort: 2–4 hours · Priority: do this before writing any code

What changes

  1. Commit all untracked work. Create develop, then four feature branches as the project README already prescribes.
  2. Move backend/.env to ~/.drishyam/drishyam-staging.env and set DRISHYAM_RUNTIME_ENV_FILE. Rotate any credential that has been shared outside the team.
  3. Clear backend/data/private_storage/, backend/backups/*.sql and generated_reports/.
  4. Rewrite Readme.md: SIH25198 → SIH26189; add MHA / NCRB Women Safety Division framing; restate the product as criminal-network intelligence rather than cybercrime evidence.
  5. Add a docker-compose.demo.yml that includes PostgreSQL and Redis so the stack can be started by anyone without the private environment file.
Result: the strongest part of the codebase stops being one command away from deletion; the repository reads as a SIH26189 submission; and any evaluator or new team member can start the stack from a clean clone.
Phase 1 — Criminal-network entity vocabulary
Effort: 2–3 days · Highest return on effort · No structural migration

What changes

FileChange
app/extraction/entities_in.py
(new)		 Vehicle — Indian registration plates: [A-Z]{2}\s?\d{1,2}\s?[A-Z]{1,3}\s?\d{4} plus BH-series. Deterministic and high-confidence.
Location — gazetteer-driven: a curated list of districts and police-station names combined with context words (at, near, PS, Thana). Open-domain NER is deliberately avoided: it is unreliable on Indian place names and would flood the review queue.

Result: uploading a single FIR PDF now yields Person, Vehicle, Location, Phone and Organisation entities, each carrying a source reference and a confidence band. The system visibly answers the entity-extraction requirement of the problem statement, which it currently cannot.
Phase 2 — Typed entity-to-entity relationships
Effort: 3–4 days · The structural centrepiece of this roadmap

What changes

  1. Add the EntityRelation model (Section 6) and one Alembic revision.
  2. New service app/services/relationship_builder.py deriving edges from NormalizedRecord rows:
    Source recordEdge produced
    CDR rowPhone —CALLED→ Phone with observed_at and duration
    Transaction rowAccount —TRANSFERRED_TO→ Account
    Chat recordParticipant —MESSAGED→ Participant, only when the source establishes the role — the existing chat_participant_identifier discipline is preserved
    FIR / surveillance recordPerson —MENTIONED_WITH→ Vehicle, Person —LOCATED_AT→ Location, Person —USED_VEHICLE→ Vehicle
  3. Call the builder from services/grounded_pipeline.py after entity resolution, inside the existing idempotent processing-run boundary.
  4. New endpoints in api/grounded.py: GET /cases/{id}/entity-relations (filterable by type, date, verification status) and POST /entity-relations/{id}/review reusing the existing review flow.
Non-negotiable invariant. Every edge must carry source_evidence_id and source_reference. An edge without provenance is never inserted. Enforcing this at insertion time is what makes the project's headline metric — Traceability Coverage — provably 100%, rather than an estimate.
Result: DRISHYAM produces an actual criminal-network graph rather than a file-similarity graph. Every edge can be traced to the file, page, row or pixel region it came from. This single change converts the product from an evidence organiser into a network-analysis system.
Phase 3 — Network analytics: influential individuals
Effort: 2 days · Cheapest large win — NetworkX is already installed

What changes

  • New module app/graph/analytics.py building a networkx.Graph from entity_relations and computing: degree centrality, betweenness centrality, PageRank, nx.bridges, louvain_communities, shortest path between two entities, and k-hop subgraph extraction for progressive UI loading.
  • New endpoints: GET /cases/{id}/network/important, GET /cases/{id}/network/subgraph, GET /cases/{id}/network/path.
  • Each ranked entity is returned with a generated explanation string, never a bare score.
{
  "entity": "98XXXXXX21",
  "entity_type": "phone",
  "metric": "betweenness_centrality",
  "rank": 1,
  "why": "This phone connects 3 otherwise separate groups in this case and
          appears in 7 records across 4 evidence files.",
  "supporting_evidence_ids": ["ev-1","ev-4","ev-7","ev-9"],
  "caveat": "Network importance indicates review priority.
             It is not an indication of guilt."
}
Result: the "identify influential individuals" requirement is satisfied with an explanation an investigator can act on and a judge can interrogate — not an unexplained score, which the advisory reports and this audit both identify as the primary interpretive risk.
Phase 4 — Source adapters for the problem statement's named sources
Effort: 3 days

What changes

Adapters are added to app/parsers/ in priority order. All emit the existing NormalizedRecord contract. No adapter is permitted to touch graph logic — this is what prevents CSV, OCR and vision parsers from producing incompatible representations of the same fact.

#AdapterExtracts
1CDR (CSV/JSON) Header auto-detection for A-party, B-party, date, time, duration, cell ID, IMEI/IMSI. Phone normalisation reuses the existing normalize(). Emits communication events and CALLED edges.
2FIR / police report (PDF, scan) FIR number, sections invoked, date, police station, complainant, accused, vehicles, locations, narrative events. PDF text layer first; OCR fallback already exists.
3Financial transaction (CSV/JSON) Largely present. Extended to emit TRANSFERRED_TO edges with participants, amount, reference and timestamp.
4Surveillance note (PDF/text/image) Persons, vehicles, locations, observation times from free-text narrative.
5Social-media export (JSON/CSV/screenshot) Handles, posts, mentions, URLs, timestamps. Lowest priority; include only if schedule allows.
Result: a single case can be built from four or more heterogeneous source types — the explicit demonstration requirement of the problem statement — with the same fictional entities appearing across several of them, which is what makes cross-source resolution visible.
Phase 5 — Temporal intelligence and criminal-network alert rules
Effort: 2–3 days

What changes

  • Add incident_window_start / incident_window_end to Case; expose them in case creation and the workspace UI.
  • New module app/services/temporal.py: event sequencing, before/after analysis relative to the incident window, communication-burst detection, and cross-source event correlation.
  • Extend alerts/rules.py. Existing fraud rules are retained but no longer dominant. Add a rule_version field to every alert.
New rule codeDetects
PRE_INCIDENT_COMMUNICATION Repeated contact between two entities in the N hours preceding the incident window
SHARED_IDENTIFIER_ACROSS_CASES One phone, account or vehicle appearing in multiple authorised cases — reuses services/cross_case.py
RECURRING_VEHICLE_AT_LOCATION The same registration plate observed at the same location across multiple sightings
COMMUNICATION_BURST A statistically unusual spike in call or message frequency within a short window
BRIDGE_ENTITY High betweenness centrality — fed directly from Phase 3
Result: alerts speak the language of criminal-network investigation rather than payment fraud. Each remains explainable, versioned, idempotent and linked to the evidence that produced it — an investigation lead, never a legal conclusion.
Phase 6 — Vision upgrade: preprocessing, quality routing, OpenAI provider
Effort: 3 days · Incremental addition, not a replacement

What changes

  1. OpenCV preprocessing — new evidence_intelligence/preprocessing.py: deskew, denoise, upscale, adaptive and Otsu thresholding, contrast adjustment, region cropping. Every variant is stored as a derived artefact linked to the parent evidence ID. The original is never overwritten — a discipline the codebase already observes.
  2. Quality report and routing — resolution, Laplacian-variance blur estimate, contrast, OCR coverage, producing a recommendation of ocr_only, vision_review or human_review_required. This is what prevents an expensive vision call on every clear printed page.
  3. OpenAI provider — new providers/openai.py implementing the existing providers/base.py protocol, using Structured Outputs with a strict JSON schema. Add openai_first to LLM_ROUTING_MODE. The model identifier arrives from OPENAI_VISION_MODEL and is verified against the live catalogue before use.
  4. Handwriting states — add a readability field with values readable, partially_readable, unreadable, alongside a literal transcription. A partially readable value is never normalised into a complete one: a fragment such as 98?7?2 must never become a phone number or a graph node.
  5. Response cache keyed on sha256 + preprocessing_version + model_id + prompt_version, so an unchanged image is never sent twice.
Result: handwritten and low-quality evidence is handled honestly. A blurry FIR page produces "unclear — review required" with the visible fragment preserved, rather than an invented value. In evaluation this is the strongest safety demonstration available, and it costs nothing to show.

Two rules that govern the whole UI

  • An unreviewed machine-extracted edge must never look identical to a human-verified edge. This is the single strongest shared recommendation across all three advisory reports and it is a product-safety requirement, not a styling preference.
  • The browser must never load the whole graph. The frontend requests an authorised, filtered subgraph and expands progressively.
Result: the differentiating chain becomes clickable end to end — graph → relationship → claim → evidence reference → original source. Most competing entries will show a graph; very few can click from a graph edge to the original pixel region it came from. The provenance data required for this already exists in FieldProvenance.source_reference and the OCR bounding boxes; only the interface is missing.
Phase 8 — Case-grounded assistant
Effort: 2 days · Trace Orb remains untouched

What changes

  • New service app/services/case_assistant.py, entirely separate from the Trace Orb help assistant.
  • It reads only database rows — entities, relations, records, alerts, audit entries. It must never use general model knowledge to fill a missing case fact.
  • It reuses the existing case-authorisation dependency in api/deps.py; permissions are enforced before any data is retrieved, not after.
  • Every factual answer returns source references, verification status and an explicit uncertainty statement.
  • All uploaded document text is treated as untrusted data. Prompt injection inside an uploaded file must not be able to change extraction policy, call tools, alter permissions or instruct the model to ignore uncertainty. This is tested adversarially, not assumed.
Result: a question such as "What evidence connects Person A with the vehicle in this case?" is answered with citations, verification states and, where appropriate, an explicit "not established by the evidence" — while the website help assistant remains provably unable to reach case data.
Phase 9 — Benchmark dataset and measurement
Effort: 3 days

What changes

Extend the existing scripts/generate_synthetic_evidence.py to produce one realistic synthetic case:

  • 2 FIR / police-report PDFs · 3 WhatsApp screenshots (one dark mode, one deliberately blurry) · 1 CDR CSV · 1 transaction CSV · 1 surveillance note
  • The same fictional entities must appear across several sources — without this, cross-source resolution cannot be demonstrated at all
  • Deliberate hard cases: one unreadable handwritten field, two similar names that must not be merged, one conflicting timestamp, one malformed file
Result: claims become measurable. The team can state accuracy per component with numbers instead of asserting a generic "AI accuracy" figure, which invites challenge and cannot be defended.

Step 12 is the winning moment. Many teams will show a graph. Very few will be able to click from a graph edge to the exact pixel region of the original document that produced it. The provenance data needed for this is already stored in this repository — only the interface is missing. Protect the schedule for Phase 7.

ReliabilityModel failure rate, retry success, idempotency behaviour

Claims the team must not make

  • No claim of guilt, criminality, or crime prediction. The system produces investigation leads.
  • No claim of live access to NCRB, CDR, banking, surveillance or intelligence databases. The prototype uses synthetic records; real connectors require lawful authorisation.
  • No claim of 100% OCR accuracy, unlimited data, real-time national analysis, or production deployment.
  • No generic "AI accuracy" percentage. Report per-component metrics instead.
  • Network centrality must be described as network importance or review priority, never as an indication of guilt.
